# Що залишилося зробити в City-map

Оновлено 14 жовтня 2026. Це план робіт, а не новий аудит. Готово локально означає, що код виправлений і перевірений у проєкті, але сайт у мережі ще може працювати на старій версії.

### Оптимізація та підготовка до релізу: усунення дублювання, узгодження логіки та дизайну

- **Усунення дублювання API клієнтів:** Видалено застарілий клієнт `src/shared/api/apiClient.ts` з ручним `fetch`. `src/components/stats/api/trackedDistrictsApi.ts` переведено на канонічний виклик `supabase.functions.invoke<TrackedDistrict[]>('get-tracked-districts')` в єдиному стандарті проєкту.
- **Уніфікація Admin API:** Створено єдиний типізований клієнт `src/pages/admin/core/api/adminApiClient.ts` (`invokeAdminApi`). `adminGeoApi.ts` та `adminUsersAPI.ts` підключені до нього без приватних дублів та з суворими типами (`UserRow[]`, `Record<string, unknown>`).
- **Синхронізація форматування дат:** Додано `formatDate(value, locale?, options?)` до `src/shared/utils/formatters.ts` із юніт-тестами; хук `useFormat` розширено функцією `formatDate` з автоматичним підхопленням мови інтерфейсу `i18n.language`. Клієнтські компоненти (`TrackedDistricts`, `PopularDistricts`, `PdfReportTemplate`) переведено на єдиний хук замість хардкоду `'uk-UA'`.
- **Синхронізація вибраної локації (Карта <-> Статистика):** Додано константу `STORAGE_KEYS.SELECTED_LOCATION`. Збереження вибраної країни та міста в `useDistrictMap.ts` автоматично підтягується в `PopularDistricts.tsx` та `accountStorage.ts` при навігації.
- **Повна синхронізація локалізації (i18n):** Виправлено шаблонні літерали для тарифів та фіч у `Payment.tsx`; покращено збирач ключів `collect_translation_keys.mjs` (додано токен `feature` та фільтрацію незавершених префіксів). 9 відсутніх ключів відновлення доступу та чекауту додано до `uk.json`, `en.json` та `pl.json`.
- **Верифікація кодової бази:** Повний `npm run check` (ESLint 0 warnings/errors, 183 vitest-тести, 152 security-тести, Vite build), `npm run check:edge` (38/38 Deno тестів), `node scripts/export.smoke.mjs` (2/2 перевірки стилів і PDF) та `node server/services/browser.smoke.mjs` (1/1 тест проксі/політики скрапера) успішно пройшли. Knip не виявив зайвих файлів та залежностей.

### Продовження 14 жовтня: атомарність подарунків

#### Наступний крок: захист повторних запитів

- Додано міграцію `20261014171920_idempotent_manual_gifts.sql`: приватний журнал `manual_gift_operations` і RPC з обов'язковим `p_request_id`. Старий виклик без request ID закритий для service_role; його використовує лише нова транзакційна обгортка. Подарунок, аудит і receipt фіксуються разом. Повтор повертає збережений результат, не пересуває строк і не відновлює відкликаний подарунок. Інші параметри/актор/одержувач з тим самим ID дають конфлікт.
- Frontend `giftCommands.ts` об'єднує одночасні однакові запити та зберігає невизначену спробу після мережевої помилки в sessionStorage, окремо для адміністратора/дії/одержувача/параметрів. Перезавантаження тієї самої вкладки зберігає ID. Після підтвердженого успіху наступне натискання — нова операція. Якщо storage вимкнено, захист повтору працює лише в поточному екземплярі контролера. Закриття вкладки або очищення storage не гарантує відновлення ID; серверні receipts не видаляються автоматично.
- Перевірено 182 frontend tests, повний check/build і Edge 38/38. Security після додаткового сценарію збою receipt — 151/151. SQL-тести перевіряють втрату відповіді/повтор, конфлікт параметрів, replay після revoke, відкат при помилках audit та receipt. Це не багатосесійний тест конкурентних PostgreSQL транзакцій.
- Обидві міграції залишаються **локальними**, разом із Edge/frontend змінами. Порядок публікації: атомарна міграція, idempotency-міграція, узгоджені Edge та frontend. Старі вкладки без requestId отримають 400 і потребують оновлення. Ця зміна не реалізує gift queue або перенесення Stripe billing.
- Додатково погоджено користувачем: подарунки одного тарифу **додаються до невитраченого залишку**, не замінюють його. На момент запису ще очікується відповідь щодо пріоритету подарункового Realtor поверх активного подарункового Premium.

- Усунуто локально частковий результат «подарунок змінено, аудит не записано»: `admin-stripe-manage/gifts.ts` викликає одну RPC `manage_manual_gift`. Міграція `20261014171051_atomic_manual_gifts.sql` створена через CLI; зміна підписки та запис аудиту комітяться або відкочуються разом. RPC серіалізує операції для одержувача advisory lock, перевіряє існування Auth-користувача і повторно читає права адміністратора/роль одержувача. Виклик дозволено тільки service_role. Збережено попередні правила строків; черга подарунків та Stripe deferral ще не реалізовані; захист повторів додано наступною міграцією вище.
- Зовнішній handler перевіряє фактичний розмір body, коректність JSON, тип action та payload; пошкоджений body повертає 400, завеликий — 413 до будь-якої операції подарунка.
- Додано dev dependency PGlite та 6 SQL-тестів справжнього PostgreSQL у пам'яті: точна тривалість, ізоляція платних/чужих записів, відкат grant/revoke при ін'єкції помилки аудиту, повторна перевірка прав, некоректні параметри, заборона прямого виклику anon/authenticated. Табличні типи звірено read-only з live. Міграція запускається двічі в тесті. Це мінімальна схема для тесту цієї RPC, **не** повний Supabase staging і **не** багатосесійна перевірка блокувань.
- Повний check: 178 frontend tests, security suite 146 tests (зокрема SQL), lint/typecheck/build успішні. Після уточнення валідації повторно пройшли security 146/146 та Edge 38/38, Deno audit чистий. npm install повідомив 0 відомих вразливостей.
- **Не розгорнуто.** Спочатку застосувати міграцію, потім Edge Function. До міграції новий handler повертатиме 503 без fallback до неатомарних записів. Канонічний `database.types.ts` поки відображає фактичну live-схему; після застосування RPC його слід згенерувати знову. Жодні робочі або тестові Stripe-підписки під час цього кроку не змінено.

### Заміна Supabase API keys — стан попереднього кроку

- `shared/supabaseKeys.js` централізує вибір ключів для Node, Edge та translation scripts: прямі `SUPABASE_SECRET_KEY` / `SUPABASE_PUBLISHABLE_KEY`, потім JSON-словники `SUPABASE_SECRET_KEYS` / `SUPABASE_PUBLISHABLE_KEYS` (поле `default`), потім тимчасова сумісність із legacy. Некоректна явно задана нова конфігурація зупиняє операцію; текст помилки не містить значення ключа. Node auth middleware використовує той самий клієнт, що й решта сервера.
- Frontend підтримує `VITE_SUPABASE_PUBLISHABLE_KEY` з fallback на `VITE_SUPABASE_ANON_KEY`; перевірка конфігурації відхиляє `sb_secret_`. Це не замінює контроль секретів у build environment. Нові ключі не внесено до env-файлів і не створено у Dashboard.
- Контактна форма під час поступового переходу приймає і старий anon, і новий publishable Bearer як гостьовий запит; авторство встановлює лише перевірений user JWT. Підроблений `user_id`, невідомий Bearer і secret Bearer не надають чужу ідентичність.
- Перевірено: повний `npm run check` — 178 frontend tests, 137 security tests, lint/typecheck/production build; після додавання сценаріїв контактної форми окремий `test:security` — 139/139; повторний `check:edge` — 38/38, аудит Deno без відомих вразливостей. Усі запуски використовували fixtures; обмеження sandbox на realpath/loopback/DNS вимагали повторного запуску поза ним. Server tests також пройшли з фіктивним новим secret key. Загальний `git diff --check` знаходить давні whitespace-помилки в широкому робочому diff; весь diff чистим не оголошуємо.

**Ротація ще НЕ виконана.** Історичний service_role, який 11 жовтня відповідав HTTP 200, слід вважати скомпрометованим до фактичного відкликання. Локальні зміни не усувають цей ризик. Немає підтвердження актуального стану ключа після 11 жовтня.

Порядок завершення ротації:

1. Перевірити всі середовища/споживачів: frontend hosting, parser server, Edge runtime, локальні та CI/admin scripts. Підготувати новий серверний secret без передачі значення через чат; новий publishable дозволений лише у frontend, secret — ніколи у змінних `VITE_*`.
2. Локально налаштовано `verify_jwt=false` для публічних `cityCountrySelect`, `get-filters-config` та гостьової `submit-contact-form`; карта вже мала відповідну конфігурацію. Приватні endpoints зберігають перевірку user JWT, AAL2 і permissions; `update-user-time` покладається також на gateway та RLS і не повинен отримати blanket `verify_jwt=false`. Потрібна перевірка саме розгорнутого gateway з новим API key: локальні mocks не відтворюють його. Підстава: https://supabase.com/docs/guides/functions/auth (перевірено 14 жовтня).
3. Узгоджено оновити сервер/Edge, конфігурацію та frontend; перевірити гостя, вхід/recovery, адмінку, читання захищених районів, контактну форму, webhook. Старі browser bundles/CDN не повинні залишити сайт залежним від legacy anon.
4. Лише після перевірки споживачів вимкнути legacy API keys у Supabase; окремо перевірити, що історичний service_role більше не виконує REST-запит. Створення нового secret не відкликає старий service_role. Після відкликання прибрати legacy fallback і старі секрети з deployment environments; очищення історії Git не замінює відкликання.

## Коротко про стан

Він збігається з server/.env; безпечна HEAD-перевірка (limit=0, без читання записів) повернула HTTP 200. Значення ключа не включати в звіти чи чат. До завершення міграції на нові ключі й деактивації legacy доступ вважається скомпрометованим. Видалення файла або переписування історії саме по собі ключ не відкликає. Доказів використання сторонніми особами цим скануванням не отримано. Офіційна процедура: https://supabase.com/docs/guides/getting-started/api-keys#rotate-a-leaked-or-compromised-key. Перевірено 2998 текстових blob з 89 локально доступних комітів (об’єкти до 2 MB); виявлений один service_role ключ за перевіреними шаблонами.

**Основа вже стала надійнішою, але проєкт ще не готовий до продажів.** Виправлено небезпечні доступи до БД і файлів, частину прав адміністратора, змішування кешу акаунтів, помилки збірки та повторне створення оплати. Додано захист парсера від читання чужих файлів і звернень до внутрішніх мережевих адрес. Узгоджено версії React/карти, оновлено PDF і низку залежностей.

Це **7 напрямів**, а не 7 дрібних задач. Частина потребує кількох окремих змін. Відсоток готовності не вказуємо: він приховав би різницю між косметичною правкою та незавершеною оплатою.

## Найближчий порядок

1. React Router 7.18.4 вже оновлено й перевірено: 9 нових тестів маршрутів, збереження захисту сторінок і повернення назад. Цей крок завершено локально.
2. Оновлення npm-залежностей і Tailwind завершено локально, root/server audit — 0. Deno-залежності також перевірено: усі 33 Edge entrypoints проходять перевірку типів, 30 Deno-тестів успішні, аудит lockfile — без відомих вразливостей. Наступний блок — підписки та промокоди.
3. Подарунки та керування оплатою розділено локально: профіль обирає найвищий чинний тариф і окремо показує платні підписки. Промокоди ізольовано локально в адмінці та Checkout; знижка зберігається у спробі оплати. Спільні правила полів/POI та міграція закриття сирих таблиць готові локально; серверні читання районів, геоданих, обраного, відстеження й AI узгоджено. Гостьові запити карти узгоджено локально; далі — явна конфігурація рейтингів та контракт/квоти AI. Для платежів ще потрібні sandbox lifecycle, звірка старих записів і узгоджена публікація.
4. Пройти неробочі користувацькі сценарії та базу даних.
5. Після цього — парсер, остаточне прибирання, загальні тести й публікація.

Автоматичні тести запускаємо після кожного пакета. Загальне ручне тестування відкладаємо до завершення основних робіт за домовленістю. Платежі спочатку перевіряємо в ізольованому тестовому середовищі; 100% знижка в робочому Stripe не замінює його.
