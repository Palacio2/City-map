# Захист запису активності — 18.10.2026

> Актуальний стан застосування міграцій і Edge на 18.10: [DATABASE-ROLLOUT.uk.md](../../DATABASE-ROLLOUT.uk.md). Наведені нижче початкові локальні перевірки не замінюють цей стан.

Локальна міграція `20261018040338_protect_activity_writes.sql` закриває прямий browser INSERT/UPDATE/DELETE у `user_activity_logs`, `user_comparison_history`, `user_district_visits`, включно з окремими column grants. Залишено SELECT лише власних рядків та backend service-role доступ. Публічний EXECUTE двох RPC відкликано; кожен вимагає auth.uid().

`track_district_visit` приймає JSON-об’єкт до 4096 байтів. `register_comparison_event` приймає масив 2–4 різних районів до 16384 байтів: це відповідає чинному UI. Обидві функції перевіряють UUID, наявність і доступність міста та району. У таблиці потрапляють лише id, city, country з БД, а не назви чи довільні поля клієнта. Визначення favorite_district також більше не копіює старий неперевірений JSON. RPC не повертають захищені характеристики районів.

Порівняння тепер створює user_stats для нового користувача, тому перша подія не губиться. Лічильники насичуються на integer max; зміна історії, денного журналу та статистики атомарна. Read-only перевірка pg_trigger підтвердила відсутність власних тригерів на цих трьох production-таблицях, зокрема sync_activity_stats; старий текст коментаря RPC про такий тригер не відповідає фактичному стану.

Межі: це валідація запису, а не доказ людської активності. Історичні дані масово не переписувались. Для staging потрібна перевірка на реальному baseline, зокрема grants та відсутності додаткових тригерів. Міграція перевірена повторним застосуванням у PGlite; вона не застосована до production.

Перевірки: 5 нових SQL regression tests, повний `npm run check` — 204 frontend / 304 security, lint, TypeScript, production build успішні. `npm run check:edge` — 38/38, dependency audit успішний.

## Продовження: серверні квоти

Наступна міграція `20261018130836_limit_activity_events.sql` додає спільні для вкладок ліміти статистики: перегляди — 60 за хвилинне вікно / 1000 за добу UTC, порівняння — 12 / 200 відповідно. Межі задані на сервері. Перевищення тихо пропускає запис аналітики, не блокує функціональність перегляду чи порівняння.

Повтор останньої прийнятої події того самого виду протягом 30 секунд пропускається. Сигнатура порівняння сортує UUID, тому перестановка вибраних районів не обходить цю перевірку. Чергування різних подій дозволене, але витрачає ту саму квоту. Це не повна дедуплікація всіх подій у вікні й не захист від створення багатьох акаунтів.

Приватна таблиця activity_event_limits містить максимум два рядки на акаунт і видаляється разом із auth.users через FK cascade. Browser/service_role не мають прямого доступу ані до таблиці, ані до helper RPC. Валідовані definer RPC блокують рядок квоти FOR UPDATE; час читається після отримання блокування, а запис аналітики й квота комітяться разом. Недійсні payload не витрачають квоту. Типи БД синхронізовано.

Додано 4 regression tests: дублікати/порядок, хвилинне вікно та ізоляція акаунтів, добова межа/UTC reset, закриті права/cascade. Попередній rollback test тепер також перевіряє відкат квоти. PGlite перевіряє логіку послідовних викликів; справжній паралельний прогін PostgreSQL ще потрібен на staging. Автоматичний retention не додано: історичні записи не видаляються без визначеного строку зберігання. Добові квоти обмежують швидкість росту, а не загальний обсяг історії. Production не змінювався.

Фінальна перевірка цього продовження: npm run check — 204 frontend / 308 security, lint, TypeScript і build успішні; check:edge — 38/38, dependency audit успішний.
